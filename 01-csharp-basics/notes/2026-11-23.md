\# Thread vs ThreadPool vs Task



\## 一、实测对比

| 场景 | Thread | ThreadPool | Task |

|---|---|---|---|

| 空任务 | 14.55 ms | 2.14 ms | 0.49 ms |

| 阻塞 50ms | 65.19 ms | 314.81 ms | 314.14 ms |



\## 二、三个结论

1\. Task 底层就是线程池，不是更快的线程

2\. 线程池线程有限（最小=核数，增长约 500ms 一个），怕阻塞

3\. 每个线程约 1MB 栈，100 线程约 100MB，生产不可行



\## 选型

\- 短小 CPU 任务 → Task.Run

\- 大量阻塞 IO → async/await

\- 长期后台循环 → 专用 Thread + 队列

\- 上千并发 → 异步，不能开线程



\## 三、线程相关类速查（按用途分五类）



\### 1. 造线程



| 类 | 是什么 | 特点 | 什么时候用 |

|---|---|---|---|

| `Thread` | 真 OS 线程 | 独占 1MB 栈，创建慢 | 长期驻留的后台循环 |

| `ThreadPool` | 线程池（静态类） | 复用线程，数量有限 | 短小任务（一般间接用） |

| `Task` | 任务抽象 | 线程池 + 状态/异常/await | \*\*默认首选\*\* |



```csharp

new Thread(Body) { IsBackground = true }.Start();  // IsBackground 必设，否则进程关不掉

ThreadPool.QueueUserWorkItem(\_ => Body());

Task.Run(Body);

```



\### 2. 管并发（谁能同时进来）



| 类 | 作用 | 一句话 |

|---|---|---|

| `lock` / `Monitor` | 互斥锁 | 同一时刻只允许一个线程进入 |

| `SemaphoreSlim` | 限流 | 允许 N 个线程同时进入 |

| `Mutex` | 跨进程互斥 | 保证程序只开一个实例 |

| `ReaderWriterLockSlim` | 读写锁 | 多读单写 |

| `Interlocked` | 原子操作 | 无锁计数器，比 lock 轻 |



```csharp

lock (\_gate) { count++; }

Interlocked.Increment(ref count);

await \_sem.WaitAsync();

```



\### 3. 传信号（等别人干完）



| 类 | 作用 | 典型场景 |

|---|---|---|

| `CountdownEvent` | 倒计数，等 N 个信号 | 等 100 个任务完成 |

| `ManualResetEventSlim` | 开关式信号（手动复位） | 暂停/继续采集 |

| `AutoResetEvent` | 一次性信号（自动复位） | 生产者-消费者 |

| `Barrier` | 阶段同步 | 多线程分阶段计算 |



```csharp

var done = new CountdownEvent(100);   // 初始计数

done.Signal();                        // 完成一个减 1

done.Wait();                          // 减到 0 时返回

```



为什么不用 `Task.WaitAll`：Thread 和 ThreadPool 的排队项没有 Task 对象可等，`CountdownEvent` 是三种方式通用的等待原语。



\### 4. 存数据（多线程同时读写）



| 类 | 作用 | 特点 |

|---|---|---|

| `ConcurrentDictionary<K,V>` | 线程安全字典 | 细粒度锁 + CAS，读多写少接近无锁 |

| `ConcurrentQueue<T>` | 线程安全队列 | 先进先出 |

| `ConcurrentBag<T>` | 线程安全无序集合 | 只放不取 |

| `BlockingCollection<T>` | 带阻塞的队列 | 空时自动等待 |

| `Channel<T>` | 现代异步队列 | 支持 await 读写 |



\*\*为什么不能直接用 `Dictionary`\*\*：它不是线程安全的，并发写入会破坏内部哈希桶，最坏情况不是报错，而是\*\*静默丢数据或死循环\*\*。



\### 5. 叫停



| 类 | 作用 |

|---|---|

| `CancellationTokenSource` | 取消的开关，可 `Cancel()` / `CancelAfter()` |

| `CancellationToken` | 取消的凭证，传进各个方法 |



```csharp

var cts = new CancellationTokenSource();

cts.CancelAfter(TimeSpan.FromSeconds(5));

await Task.Delay(1000, cts.Token);

```



\### 6. 计时与诊断



| 成员 | 作用 |

|---|---|

| `Stopwatch` | 高精度计时 |

| `Environment.ProcessorCount` | CPU 核数 |

| `Environment.CurrentManagedThreadId` | 托管线程 ID（≠ OS 线程 ID） |

| `Thread.Sleep(ms)` | 阻塞当前线程 |

| `ThreadPool.GetMinThreads/GetMaxThreads` | 查线程池配置 |



\## 四、选型速查



| 要做的事 | 用什么 |

|---|---|

| 长期跑的后台循环 | `new Thread(...){IsBackground=true}` |

| 短小的计算任务 | `Task.Run` |

| N 个线程互斥 | `lock` |

| 最多 5 个并发 | `SemaphoreSlim(5)` |

| 等一批任务完成 | `Task.WhenAll` / `CountdownEvent` |

| 多线程共享字典 | `ConcurrentDictionary` |

| 生产者-消费者 | `BlockingCollection` / `Channel` |

| 长任务能被叫停 | `CancellationToken` |

| 跨进程单实例 | `Mutex` |

| 无锁计数器 | `Interlocked` |



\## 五、上位机的坑



```csharp

// ❌ 错误：100 台设备各起一个 Task 去同步读串口

foreach (var device in devices)

{

&#x20;   Task.Run(() =>

&#x20;   {

&#x20;       var data = device.ReadBlocking();   // 阻塞 50ms，占住线程池线程

&#x20;       Save(data);

&#x20;   });

}

```



后果：线程池只有 8 个线程，100 个任务排队 → 采集周期从 50ms 变成 600ms，设备越多越慢。



正确方向：



```csharp

await device.ReadAsync();        // 真异步，等待期间不占线程

```



或专用线程 + 队列：



```csharp

new Thread(() => { while (running) { 从队列取任务; 处理; } }) { IsBackground = true }.Start();

```



\## 六、面试一句话



> `Task` 底层就是线程池，不是更快的线程。线程池线程数有限且增长慢，适合短小的 CPU 任务；大量阻塞操作会把线程池占满导致排队，这时应该用 `async/await` 真异步，或用专用线程加队列。100 个线程仅栈空间就要 100 MB，生产环境不可行。
